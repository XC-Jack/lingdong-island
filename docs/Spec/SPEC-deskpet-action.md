## 起因

用户 2026-11-12 给了参考视频（`什么时候听见这个才能不笑#奶蛙 #捧腹大笑`），说
「这是这个角色的一些标志性动作，所以我希望到时候可以加上去」，

## 一、目标

给桌宠增加「动作」这一层，与「情绪（mood）」分开；素材来自用户给的参考视频，
自己在桌面上点一下（或从右键菜单）就能看。

第一支动作是**大笑**（2026-11-12 第五轮）；第二支是**打滚**（第六轮，用户
「就做挥手打滚」）。当时「挥手」没做成——那段视频里根本没有挥手动作（详见 7.9），
**第七轮用户另找了一段可灵生成的视频，挥手这一支才补上**（详见 7.13）。

## 三、预期行为

1. 宠物空闲时跟现在完全一样（呼吸 + 转身 + 旋转把手），动作层不可见。
2. 在宠物身上**点一下**（按下与松手之间没发生拖动）→ 播一次大笑，约 7.2 秒，播完自动回到站姿。
3. 大笑播放期间再点一次 → 从头重播（不叠加、不排队）。
4. 动作播放期间按住拖动 → 窗口照常能拖走，动作不中断。
5. 动作播放期间按住底部把手 → 照常转身。
6. 动作只影响「形象层」，不影响窗口尺寸、位置、置顶状态。
7. 三套皮肤里只有「我的原图」有动作素材；**另外两套点了不播任何东西**（不报错、不空白）。
8. sprite sheet 按「同一高度、水平居中」摆放，与四视图转身的构图规则一致，播放时脚底不跳。
9. （第六轮）右键菜单里有「再来一次大笑」和「打个滚」，点完立刻播对应的那支。
10. （第六轮）两支动作**各按自己的帧数定时**：大笑 108/15 = 7.2 秒、打滚 82/15 ≈ 5.5 秒；
    短的那支不会因为共用一个常量而多空站一段。
11. （第七轮）右键菜单里有「挥挥手」，点完立刻播挥手；它同样按自己的帧数定时
    （34/15 ≈ 2.3 秒），且只播真正的挥手段，不含挥完手站着不动的那一段。

## 七、自检记录

### 7.1 素材是怎么来的

用户给的参考视频 `什么时候听见这个才能不笑#奶蛙 #捧腹大笑_...mp4`：576×1252、30fps、573 帧、19.1 秒。

抽帧只取「大笑 + 捂头」那一段，避开开头结尾的静止镜头：

```
ffmpeg -v error -ss 1.4 -to 8.6 -i <视频> -vf "fps=15" .tmp\niwa\laugh\%03d.png -y
```

得到 108 帧。原片顶部有 iOS 状态栏（时间、电量）、底部有播放器按钮栏，都要裁掉，否则桌宠身边会挂着一排按钮。裁框 `BOX = (34, 334, 518, 994)`，即 484×660。

### 7.2 抠图：三个坑

脚本 `.tmp/niwa/cut_frames2.py`（`bg_mask` / `flood_outside` / `carve_enclosed` / `cut` 四个函数），输出 `.tmp/niwa/laugh-cut/`。

**坑 1：地面阴影不是白的。**  
第一版用「低饱和 + 高亮度」一刀切，地面阴影实测 chroma 中位 6、`mn` 中位 247，被当成前景留下来，每帧脚下一块白斑。改成从四边泛洪取「外部连通的背景」才对——阴影在脚下，和外部背景连通，会一起被挖掉。

**坑 2：两腿之间那块背景从外面进不去。**  
腿和地面把它围成一个封闭区，泛洪够不着，留一块白斑。解法 `carve_enclosed`：把「封闭的、≥300 像素、质心在下半部（`mean(y) > h*0.5`）」的连通块也挖掉。位置条件很关键——牙齿同样是「中性且亮」的颜色，靠「在上半部」保住它。实测每帧挖掉约 8800 像素（x220–337 y495–607）。

**坑 3：边缘发白。**  
和正视图同一类问题（alpha matte 污染），沿用同一套去污染公式 `F = (C − (1−a)·255) / max(a, 0.35)`，只作用于 `0.02 < a < 0.995` 的过渡带。

最终判据参数：`BG_CHROMA = 52`、`BG_MIN = 170`。**放宽到 52 的依据是实测**——角色肚子（奶白）是 `[248,218,121]`、chroma 123，远高于阈值，不会被误伤；真正的中性色（白背景 0、地面阴影 6）远低于阈值。

### 7.3 统一舞台

逐帧单独裁会让角色在播放时左右乱跳，必须固定舞台。全体 108 帧取并集包围盒 `(16, 14, 471, 645)` → 455×631，缩放到高 220（`TARGET_H = 220`），宽按比例 = 159。输出 `.tmp/niwa/laugh-final/`，108 帧、159×220。

### 7.4 体积：为什么是两行、为什么 108 帧不砍

实测各方案：

| 方案 | 体积 |
|---|---|
| 108 帧 PNG 独立文件 | 3437 KB |
| 108 帧 WebP q88 独立文件 | 923 KB |
| 54 帧单行 sheet WebP q86 | 390 KB（8586×220） |
| **108 帧两行 sheet WebP q84** | **744 KB（8586×440）** |

最初打算用 54 帧单行（390 KB）。**但 108 帧单行的宽度是 108×159 = 17172px，超过 WebP 单边 16383 的上限**，编码器会截断——所以只要保留 108 帧就必须折行。折成 54 列 × 2 行后是 8586×440，宽度回到 8586。

最后选 108 帧两行（744 KB）：比 54 帧多一倍体积，但保留原片全部帧、不动节奏。整个应用体积 744 KB 换来一段 7.2 秒的完整动作，可接受。

### 7.6 两个断言写错、改对（本轮教训）

**教训 1：`<clipPath>` 里的元素 `getBoundingClientRect()` 恒为 0。**  
P9h-3 第一版量 `clipPath rect` 的 `getBoundingClientRect()`，跑出 `{"动作":{"左":0,"右":0,"底":0},"站姿":{"左":45.2,"右":146,"底":209.3},"中心偏差":95.6}` —— 假红。`<clipPath>` 的内容不参与渲染，没有布局盒。改成直接读 `x` / `y` / `width` / `height` 这几个用户坐标属性，它们和站姿 `<image>` 的属性在同一坐标系里，可以直接比、不用换算 DPI，阈值随即收紧到 ≤1。

**教训 2：断言的先后顺序会影响结果。**  
P9h-1 触发的那次笑要 7.2 秒才结束。第一版把「拖一把不该触发」放在「播完回 idle」之前，读到的是还在播放中的 `laugh`，会把「拖动没触发动作」误判成失败。已把「等它播完」提到拖动测试之前，并在代码注释里写明原因。

### 7.8 白边没抠干净 + 配色统一（用户实测反馈后重做）

用户 2026-11-12 反馈：「捂头的动作白色背景没有扣干净；还有很多地方背景没有扣干净，你自己在仔细弄一下 / 色差你可以统一一下，取个中间值」。

**白边根因**：v2 的 `carve_enclosed` 只挖「封闭 + ≥300 像素 + **质心在画面下半部**」的背景块。捂头时两臂与头围出的两块纯白区在**上半部**，被位置条件保护住 → 留成白三角。位置判据本来是为了保护牙齿（牙齿也中性且亮）。

**量化（判据 `al>40 & min>235 & chroma<22`）**：

| 版本 | 残留像素 | 单帧最高 | 有残留帧数 |
|---|---|---|---|
| v2（原交付） | 10149 | 669 | 49 |
| v3（加 min 通道 + 外圈暗度） | 2974 | 527 | 26 |
| **v4（改用「严格白占比」）** | **1289** | **147** | **26** |

**v4 的判据怎么来的（关键）**：扫全部 108 帧的 255 个封闭块，逐块算「块内严格白像素占比」，两组之间是空的——

| 类型 | 严格白占比 |
|---|---|
| 白背景空洞（101/088/089/086/100/085/087/084/094/098/096/099 等） | 0.78 ~ 0.87 |
| 牙齿、肚皮高光、手臂高光（全部） | ≤ 0.45 |

取 **`CARVE_STRICT_FRAC = 0.5`** 卡中间。这条判据**不依赖位置、不依赖外圈暗度**。
失败的尝试：v3 用「min 通道 > 225 且外圈暗像素 < 0.5」——088/087/093 那批白三角外圈暗度实测 0.51~0.52，刚好卡在线外没被挖；把 `BG_CHROMA` 放宽到 60 / `BG_MIN` 放到 148 则**反把身体高光当背景咬掉**（腰部出现黑色缺口）。

**剩下 1289 像素不是背景，是手臂上的高光条**（`.tmp/niwa/v4-100.png` 4× 放大目视确认：一块窄长白条贴着手臂外轮廓，位于手臂与躯干之间的三角区）。直接挖会在手臂上凿洞，所以改成**换色不换 alpha**——脚本 `.tmp/niwa/build_sheet.py` 的 `fix_white_rim()` 用 19×19 邻域内的身体色中位替换 RGB，alpha 原样保留。白条变黄条，看起来就是一道高光。成品 sheet 里严格白残留从 1289 降到 **38 像素**。

### 7.9 第二支动作「打滚」+ 为什么没有「挥手」（第六轮）

用户 2026-11-12 原话：「就做挥手打滚」。

**挥手这一支做不出来**（先说不做的）：把整段 19.1 秒视频按 10fps 抽成 176 帧
（`.tmp/niwa/f10/`），用「手/脚深棕像素的最低点」逐帧扫手抬到多高——
手抬得最高的帧是 34/35（y=364）、20/32（y=368）、112（y=368），
全都只有 0.2 秒左右的一抬，而且是大笑时抬手捂头/捂肚子的一部分，
**没有一帧是「手举起来来回摆动」的挥手**。这支动作必须另找素材或 AI 生成视频，
不在本轮范围。

**打滚的素材**：同一段视频 12.0–18.4 秒「倒地 → 躺地打滚 → 起身」，15fps 抽 96 帧
（`.tmp/niwa/roll/`），可用 **1–82**：83–96 是同一张站姿重复 14 遍（逐帧差异 ~0.0~0.05），
82 是起身那一跳（差异 18.7，最大跳变）。

**打滚和大笑的三处参数差异**（这是本轮的真正难点，不能照抄大笑的脚本）：

1. **背景阈值必须收紧**：`BG_CHROMA` 52→**20**、`BG_MIN` 170→**235**。
   躺下时肚皮正对光源，高光亮到 `(254,235,203)`（min=203、chroma=41），
   恰好落进大笑用的宽松阈值里，会被**整块挖掉**——实测 025 帧肚皮上挖出一个指甲盖大的缺口。
   背景纯白 min≈250，靠 min 通道就能干净分开。
2. **地面阴影必须单独去**：站姿拍时阴影被裁框切掉大半；躺下时身体贴地，
   阴影与前景区连成一片，深色桌面上是一块灰斑。做法是从四边出发沿「低彩度 + 中低亮度」
   扩散（`passable = bg | (chroma<45 & min>185 & min<232)` 再泛洪）。
   实测只吃掉前景 **2.02~2.04%**，全是阴影；身体 chroma>100 挡住、手（深棕 min<60）挡住、
   牙齿在口腔内外部泛洪进不去。
3. **封闭阴影碎块**：双脚围住的阴影泛洪进不来。按「`chroma<23` + `min>200` + `min<232` + 面积≥8」挖。
   `chroma<23` 是为了**保护眼球白**（实测眼球白 chroma≈43）。

**清残留白渣**：脚边常挂几粒没被泛洪抓到的白点（82 帧里 80 帧有，单帧最多 60 像素），
深色桌面上很明显。用 `keep_largest(alpha, thr=0.5)` 只留最大连通块，
再用 `MaxFilter(5)` 膨胀保住羽化边——残留从 897 像素/80 帧降到 **319 像素/62 帧**。

**阴影线**：`SHADOW_MIN_FLOOR` 185 → **160**。地面阴影实测最暗 `(217,201,175)`
（min=175、chroma=42），原 floor 185 正好把它漏在门外，深色桌面上一道灰影线。
160 仍远高于身体 min（身体黄 min≈44、肚皮 min≈121），不会咬到角色。

**成品**：`src/renderer/src/assets/pet/bean-roll.webp` = **3960×880**、24 列 × 4 行、
每格 **165×220**、82 帧、WebP q84、**351330 B / 343.1 KB**。
配色位移 `(-4,-7,-12)` 向皮肤中点靠，成品身体黄中位 `(236,176,63)`。

**代码怎么接的**：`skinPhoto.tsx` 把「动作 → 素材参数」抽成 `ACTION_SPECS` 表
（`cols` / `frames` / `cellRatio` / `src`），并新增 `actionDurationMs(action)` 按各自帧数算时长。
**为什么不能共用一个 `ACTION_DURATION_MS` 常量**：大笑 108/15=7.2 秒、打滚 82/15≈5.5 秒，
写死一个会让短的那支播完后空站 1.7 秒。P9i-4 就是守这条的。

**触发入口**：右键菜单加「再来一次大笑」/「打个滚」两项，主进程 `win.webContents.send('pet:action', ...)`，
渲染层 `onPetAction` 收到就播。**为什么不做鼠标手势**：「打滚」没有自然的手势，
塞成双击会跟「双击转回正面」抢，塞成长按会跟拖动抢。

**验证（[实测]）**：`npm run typecheck` EXIT=0、`npm run build` EXIT=0
（`bean-roll-BgY4YbMM.webp 351.33 kB`）；`e2e-deskpet-out` **PASS（69 过 / 0 败）**，
新增 P9i-0 ~ P9i-7 八条；回归 `e2e-deskpet` 33/0、`e2e-m2` PASS、`e2e-head-order` 14/0、
`e2e-collapse-order` 22/0、`e2e-settings-shell` 51/0（`.tmp/regress-roll.log`）。

**测试里踩的假红**：P9i-0 第一版读出来 `{"实际":"laugh"}`。原因：前一条 P9h-6
刚在胶囊皮肤上点了一下，胶囊没有动作素材、DOM 里不渲染动作层，

**未验证**：①打滚播起来真人看是什么观感（尤其躺下变宽后 190 宽的窗口够不够，
现在按 140 单位高度换算下来格宽约 105，窗口内左侧居中，理论不裁）②两支动作连着点会不会有手感问题
（代码上会先清旧定时器，但没真人试）。

### 7.10 打滚「身体残缺」+ 三张皮肤的白缝 + 右键多出边框（第七轮，用户实测反馈后修）

用户 2026-11-12 原话：「我一右键就会多出来一个边框；还有就是打滚扣的不好，身体有残缺；
我现在又发现了一个之前没发现的，截图二，就是原版的图片上手部和手和肚皮的夹缝都有一点白色背景没扣好；
还有就是我刚刚截图，灵动岛没有信息提示弹出」。前三条本轮已处理，第四条另行排查。

**（一）打滚「身体残缺」= 阴影泛洪顺着肚皮高光咬进身体**

不是帧被裁，也不是连通块被切。逐项排除过的：82 帧逐帧查贴边（只有 3~27px 的边缘细条）、
`alpha>0.5` 连通块无一帧出现第二个 >50px 的块、内部透明洞 0 像素、
用 `(ch>35)|(mn<200)` 判严前景只被抠掉 0.05%、封闭背景块 ≥40px 的 0 个。

真因在阴影判据：
```python
passable = bg | ((ch < SHADOW_CHROMA_MAX) & (mn > SHADOW_MIN_FLOOR) & (mn < SHADOW_MIN_CEIL))
reach = flood(passable)
```
它从四边泛洪，会**顺着肚皮上缘「亮且低彩度」的高光一路咬进身体**。帧 046 被吃掉的非背景像素
**4663 个**（RGB 中位 `[235,224,211]`），第二大的块 **600px 就在 `x220–342 y374–403`**，
成品上正是「像被啃掉一口」的缺口。修法是给阴影判据加**地面带限制**：
```python
SHADOW_BAND = 70
fg_ys = np.nonzero(~bg)[0]
band_top = max(0, int(fg_ys.max()) - SHADOW_BAND) if len(fg_ys) else 0
shadow_ok[:band_top, :] = False   # 只允许贴着角色最低点往上 70 行以内当阴影
```
效果：帧 046「非背景却透明」**5748 → 4522**、帧 030 **6121 → 4827**。

**（二）白 halo = 透明区还留着纯白 RGB**

`cut()` 只对 `0.02<alpha<0.995` 的窄带去污染，**alpha 更小的像素 RGB 仍是原图的纯白**；
`resize(..., LANCZOS)` 是逐通道插值、非预乘 alpha，白就被混进边缘。
修法是新增 `fill_transparent(rgb, alpha, r=7, iters=3)`：把透明区的 RGB 迭代填成邻域身体色，
再缩放就没有白可混。**预乘 alpha 缩放这条路走过、不能用**——实测白边像素从 0 涨到 161。

**（三）三张原图皮肤的「夹缝白」**

先量：`bean-photo.png` 里「不透明且 min>235 & chroma<20」只有 **7px**（`x36–272 y338–343`，
正是左右手与肚皮之间那两条缝）；侧图、背图都是 0。把这几点放大到 12× 对照原图，
确认原图腋下本身就是一条白缝（手臂与肚子之间背景透出），不是抠坏了。

修法是 `.tmp/niwa/carve_photo_holes.py`，判据**只看绝对颜色，不跟背景比**：
```python
HOLE_MIN_CHANNEL = 230   # min 通道
HOLE_CHROMA_MAX  = 25    # chroma
MAX_HOLE         = 300   # 奶白肚皮 7000+，靠这条兜一层
```
第一版拿「与透明区背景中位色的差 < 6」当判据，只挖到 2 像素就收工——
因为成品 PNG 的透明区虽然 alpha=0，RGB 却还留着**身体黄**（算出来 bgc=[245,219,111]），
真正的白缝离它 126，全被挡在门外。改判据后：正面挖 **10px**、背面挖 **3px**、侧图 0。

**（四）右键多出的那圈边框 = Chromium 焦点环**

用户截图（m03690）里那圈线量出来是 `x30..267 / y36..348`，正好 **238×313 物理像素**，
等于宠物窗口 190×250 DIP × `devicePixelRatio 1.25`；线的颜色 **(229,151,0)**，
而本机 `HKCU\Software\Microsoft\Windows\DWM\AccentColor = 0xFFD47800` → RGB(212,120,0)。
**矩形严丝合缝贴合窗口 + 用系统强调色画 = Chromium 自 100 版起的 `:focus-visible` 焦点环。**

修法（`src/renderer/src/petwin/petwin.css`）：
```css
.petwin:focus,
.petwin:focus-visible {
  outline: none;
}
```
**为什么该关掉**：这个窗口没有键盘操作，焦点环没有意义；而且它是无边框透明窗口，
环一出来就等于给桌宠套了个方框。

**验证手法（值得记）**：脚本里 `el.focus()` 不会让 `:focus-visible` 为真（Chromium 认为那是
鼠标交互），**必须用 CDP 派发一次真实的 Tab 键**。负对照也不能用 `<style>` 注入
（`pet.html` 的 CSP 会拦），要走 CSSOM 的 `sheet.deleteRule`。实测三轮：

| 轮次 | 状态 | 边框 |
|---|---|---|
| 原始（未激活） | `focus=false focusVisible=false outlineStyle=none` | 无 |
| 真鼠标点一下让窗口激活 | 同上 | 无 |
| **删掉 CSS 那条规则 + Tab** | `focusVisible=true outlineStyle=auto outlineColor=rgb(229,151,0)` | **出现**（琥珀色边框计数 top48/bot113/left76） |

第三轮的颜色 `rgb(229,151,0)` 与用户截图里 `(229,151,0)` **逐位相同**，这是「就是它」的硬证据。

**全量复检**：`bean-roll.webp` 3960×880 / 82 帧 / 每格 165×220 / WebP q84 /
**343328 B**；整张 sheet 严格白残留 **3px**、边缘亮带（halo 指标）**0px**。
三张皮肤：正面 130918 B、背面 112981 B、侧面不变 98175 B。

**e2e 新增 P9j 三条**（`scripts/e2e-deskpet-out.mjs`）：
- `P9j-1` 源码断言 `petwin.css` 里有 `.petwin:focus { outline: none }`

**为什么 P9j-3 必不可少**：只断言「现在没有边框」属于假绿——把整段 CSS 删掉也能过。
必须有「删掉它就红」的对照，这条断言才有判别力。

**（五）「灵动岛没有信息提示弹出」= 横幅发给了宠物窗口**

### 7.11 横幅图标显示不出来（第八轮，用户实测反馈后修）

用户 m04725 原话：「还有就是这个图标怎么显示不出来」。附图 m04724（123×46）是岛横幅截图：
深色圆角条，左边一个**灰方块**是应用图标位，右边文字「屏幕截图已复制到…」「已自动保存到屏幕截…」。

**先排除三个不是原因的方向**：

| 猜测 | 实测结论 |
|---|---|
| 图标解析失败、`icon` 是 null | **不是**。紫色 fallback 文字没出现在图标位（紫像素在 `y10~20 x34~120`，是标题色），说明走的是 `<img>` 分支 |
| CSP 挡了 `file:` | **不是**。`src/renderer/index.html:8` 的 CSP 是 `img-src 'self' data:`，确实没有 `file:`；但在构建产物页面（源本身就是 `file://`）里建 `<img src="file:///...">` → `{"outcome":"load","naturalWidth":48,"csp":[]}`，**CSP 违规数组为空** |
| 图标本身是灰的 | **不是**。`%APPDATA%\lingdong-island\icon-cache\notify-ScreenSketch_8wekyb3d8bbwe.png`（48×48）放大到 192×192 是**彩色的**：红色虚线框 + 灰色剪刀 + 蓝色圆点 |

**真因：源不同，`file://` 子资源被 Chromium 底层拦掉。**

开发预览版的页面源是 `http://localhost:5173`（`ELECTRON_RENDERER_URL`），打包版是 `file://`。
`.tmp/probe-icon-origin.mjs`（node 起静态服务器挂 `out/renderer`，electron 加载 `http://127.0.0.1:5199`）
三组对照，结果完全一致：

```
{"file":"error","data":"load:48","csp":[]}   ← 原 CSP
{"file":"error","data":"load:48","csp":[]}   ← CSP 显式放行 file:
{"file":"error","data":"load:48","csp":[]}   ← 直接 navigate 到副本
```

**`file:` 一律 error、`data:` 能 load:48、CSP 违规数组全空** —— 不是 CSP 规则拦的，是「http 源引用
file:// 子资源」这条更底层的限制。`<img>` 静默失败，只剩 `.banner-icon` 那层
`background: rgba(255,255,255,0.08)`，在深色横幅上就是一块空灰底。

**为什么用户会在打包版里也看到**：置物架图标（`src/renderer/src/App.tsx:703`）走同样的 `file:///`
写法，而用户当时跑的正是开发预览版；打包版同源能加载，所以他之前没发现。

**修法：主进程注册自定义协议 `ldapp://`。**

新增 `src/main/localFileProtocol.ts`：

- `protocol.registerSchemesAsPrivileged([{ scheme: 'ldapp', privileges: { standard: true, secure: true, supportFetchAPI: true, bypassCSP: false } }])`
  —— **必须在模块顶层调用**，早于 `app.whenReady()`，放进去就失效了。
- `protocol.handle('ldapp', ...)`：从 `url.pathname` 取单段 `encodeURIComponent` 的绝对路径 → `decodeURIComponent`，
  过 `ALLOWED_EXT` 白名单（`.png .jpg .jpeg .webp .gif .bmp .ico .svg`）+ `existsSync` + `isFile()`，
  最后 `net.fetch(pathToFileURL(target).toString())` 返回（Electron 官方做法，自动带对 content-type）。
- `bypassCSP: false` + CSP 里显式写 `img-src 'self' data: ldapp:` —— 不靠放宽安全边界解决问题。

三处接线：`src/main/index.ts` 的 `whenReady` 里 `setAppUserModelId` 之后插 `setupLocalFileProtocol()`；
`App.tsx` 的 `iconUrl()` 与置物架图标都改成 `ldapp://local/${encodeURIComponent(path)}`。
**拼接规则主进程与渲染层必须一致**，两边注释互相点名。

**验证（[实测]）**：

| 项 | 结果 |
|---|---|
| `.tmp/probe-ldapp.mjs`（http 源 + 真实主进程） | `{"file":"error","ldapp":"load:48","origin":"http://127.0.0.1:5201"}` |
| `npm run typecheck` / `npm run build` | EXIT=0 / EXIT=0（`bean-roll-C0Y-dx-n.webp 348.00 kB`） |

### 7.15 白边第二版：上一版的指标偏乐观（第十轮返工）

用户 2026-11-13 17:19 原话：「打滚和大笑暗0.2看看；挥手的白边还是有，你再仔细扣一下」。

**上一版为什么没过（[实测]）**：7.14 那份「边缘−内部差 3.14」是拿「整个不透明内部」当分母，
内部含大片亮奶白肚皮，把差值摊薄了。换成**局部环比**——半透明带 `0.05<a<0.90` 对比
「紧贴边缘那一圈实心像素」（`solid` 减 `MinFilter(3)` 腐蚀一环）——重测：

```
修白边前  +79.21
7.14 版   +8.66      ← 用户说「还是有」是对的
```

**再挖一层真因**：不只是「抗锯齿带混了背景白」，**素材本身在身体外缘就有 3~5px 宽的亮高光渐晕**。
按到背景的距离量源帧 `.tmp/wave/070.png` 的颜色：

```
距背景 1px (251,237,224)   3px (228,190,153)   5px (187,122,66)   7px (190,112,38)
      9px (197,112,29)    11px (201,113,26)   15px (205,119,25)
```

也就是说 7.14 的「把内部颜色往外推」推的仍是这圈高光，等于把亮边又铺了一遍。

**走过的弯路（都别重试）**：
- 掩码先内缩 6px 取本体色再外推（`.tmp/wave_rim5.py`）：偏白压到 0.1%，但边缘反比内部暗 **−36.75**，变成黑边。
- 按亮度差自适应混色（`.tmp/wave_rim6.py`，`LO,HI=12,44`）：差 **−20.28**，仍偏暗。
- 以「紧贴边缘的实心像素」为色源外推 6 圈（`.tmp/wave_rim7.py`）：局部环比 **+22.66**，比 7.14 更差。
- 整图外推 400 圈：10 分钟跑不完，不可行。

**最终修法（`.tmp/wave_rim9.py` / 落地脚本 `.tmp/wave_rim11.py`）**——不再区分「高光/本色」，
直接把**整圈外缘（含外部透明区）的 RGB 全部替换为本体色**：

```python
solid = alpha >= 250
core  = MinFilter(2*12+1)(solid)        # 内缩 12px 取「可信本体」
body  = spread(a, core, iters=20, step=2)   # 逐圈外推填满全图
rgb   = body + delta                    # 全图都是本体色，alpha 负责成形
```

关键点：**透明区的 RGB 也必须填成本体色**，否则 LANCZOS 缩小时会把外部白背景卷进轮廓
（第一版只替换图案内部、留着透明区白 RGB，测出来还是 +77.58）。
