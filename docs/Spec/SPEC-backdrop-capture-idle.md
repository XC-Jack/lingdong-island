# SPEC：玻璃底图抓屏改为「空闲档」

- 日期：2026-11-28
- 分支：`collapsed-lyric-bar`
- 状态：进行中

## 1. 目标

消除展开/切页/收起动画期间的周期性卡顿。实测根因：渲染层展开态每 1.5s 拉一次桌面底图，主进程 `desktopCapturer.getSources` 每次阻塞约 300ms（与缩略图尺寸无关），期间浏览器进程不提交帧，岛整体冻结。

## 2. 修改范围

- `src/main/index.ts`：抓屏入口增加「最近改过窗口尺寸就拒绝」的时间闸；记录 `lastBoundsChangeAt`。
- `src/renderer/src/App.tsx`：底图拉取节奏改为空闲驱动——用户最近 2.5s 没有指针/键盘操作才抓；展开态成功后 8s 再抓，收起态 20s；失败 1.5s 重试。
- 同步文档：`docs/facts/本机约束与踩坑.md`（300ms 实测）、`docs/facts/技术方案.md` 或视觉规范中的刷新频率、`docs/状态.md`。

## 3. 预期行为

- 展开、收起、切页、点「词」等任何动画期间不再触发抓屏，帧间隔恢复稳定。
- 用户停止操作约 2.5s 后才会刷新底图（每次刷新主进程仍会阻塞约 300ms，但此时没有动画在跑）。
- 底图外观、模糊参数、亮度自适应逻辑不变；只是刷新变慢。
- 抓屏失败仍静默回退静态玻璃，不影响可用性。

## 4. 必要依赖

无新增依赖。沿用 Electron `desktopCapturer`。

## 5. 验收条件

- [x] CDP `Page.startScreencast` 在 10+ 次展开/切页/收缩中，玻璃主题下无 >40ms 合成帧间隔（改前实测 320~365ms 多处）。
- [x] 同一脚本 mono 主题（不抓屏）与 glass-light 主题的帧间隔分布一致。
- [x] 静止 2.5s 后底图仍会刷新（底图 URL 变化可观测）。
- [x] `npm run typecheck`、`npm run build` 通过。
- [x] 相关 e2e（`e2e-collapsed-lyric`；仓库没有底图专项 e2e）通过。

## 6. 不做什么

- 不改抓屏实现方式（不换成持续 `getDisplayMedia` 流，避免系统捕获指示条与额外复杂度）。
- 不改缩略图比例与模糊参数（实测缩小缩略图对耗时无帮助）。
- 不动展开动画本身（首帧约 70~80ms 的首次挂载开销另行观察）。

## 7. 自检记录

**改前基线 [实测]**（`.tmp/probe-frames2.mjs`，CDP screencast + 连续 3 轮「网格→音乐→网格」等）：
- `glass-light`：多处 `worstGap` 320 / 365 / 317 / 320ms；总帧率 40.1fps。
- `mono`（不抓屏）：全程无 >40ms 空档，943 帧 / 15.6s = **60.4fps**。
- 单独抓屏耗时探针（`.tmp/capcost`，1920×1080 / sf1）：0.35→672×378、0.25→480×270、0.15→288×162、0.08→154×86，各 4 次，全部 **300±7ms**。

**改后 [实测]**：
- `glass-light` 同一脚本：10 次交互全部 0 个 >40ms 空档，最大 37ms；903 帧 / 17.5s = 51.5fps（screencast 基线本身随负载波动）。
- 空闲探针（`.tmp/probe-idle-refresh.mjs`）：启动后 6s 内 `.island-backdrop` 出现（data URL 1249B）；展开后空闲 8s 变为 4357B——说明「停手 2.5s 后刷新」仍生效。
- `npm run typecheck` EXIT=0；`npm run build` EXIT=0。
- `node scripts/e2e-collapsed-lyric.mjs`：**PASS 43 / 0**。

**未验证**：
- 首次展开仍有约 80ms 长任务（mono 下同样存在，不是抓屏引起），用户是否能感知未验证。
- 真实桌面换窗口后底图最多晚 8s（展开）/ 20s（收起）更新，观感待真人确认。
- 未在安装版（真实用户数据、真实音乐会话）复测。
