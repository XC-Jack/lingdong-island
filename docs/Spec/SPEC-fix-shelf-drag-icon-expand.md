## 一、目标

1. **置物架条目能拖出岛，拖到别的应用里**（剪映、资源管理器、聊天窗等）。这是功能缺失，不是 bug。
2. **同一个 `.lnk` / `.exe` 在置物架上显示自己的图标**，不再全系统共用第一张。
3. **有应用窗口盖在岛下面时，展开/收起不卡、不出现显示不完整**。

## 二、现象与根因

### 问题二：拖不到别的应用

**根因 [实测]**：`grep -rn startDrag src/` 只命中 `node_modules/electron/electron.d.ts`，业务代码**零调用**。置物架格子的 `draggable` + `onDragStart`（`App.tsx:1183-1206`）只做了 `setData('text/plain', it.id)`，服务的是**架内互换位置**。Chromium 的 HTML5 拖放只在同一渲染进程内传递数据，拖到剪映/资源管理器时对端收到的是空拖拽，光标显示禁止。

**修法**：`webContents.startDrag({ file, icon })` 才能发起**系统级**文件拖拽（Electron 唯一途径）。它必须在 `dragstart` 里同步调用才有效（拖拽会话由 Chromium 在该事件内接管）。

### 问题三：图标不对

**根因 [实测]**：`src/main/shelfStore.ts:130-132`

```ts
const key = isFolder ? '_folder' : ext ? ext.toLowerCase() : '._none'
const png = join(iconDir, `${key.replace(...)}.png`)
```

缓存 key 只用**扩展名**，真实路径不参与。于是全系统所有 `.lnk` 共用 `%APPDATA%\lingdong-island\icon-cache\.lnk.png`——实测该文件 1179 B、生成于 2025-11-07，内容是**别的应用**的快捷方式图标（深色卡片 + 紫色胶囊 + 齿轮），与用户截图里置物架上那个错误图标一致。用户桌面的 `打游戏前请显存.lnk` 本该是蓝色底 + 箭头的快捷方式图标。

**修法**：真实文件存在时把缓存 key 改成「扩展名 + 路径哈希」，一个文件一份图标；文件不存在（失效条目）仍按扩展名共用占位图标。

### 问题一：有覆盖窗口时展开卡顿 / 显示不完整

**探针结论（本机 1536×960 @125%，`.tmp/probe-*.mjs` 系列）**：

| 场景 | 结果 |
| --- | --- |
| 无负载 | 帧间隔 p90=17ms，岛超界 **0/95** 帧，窗口 t=244ms 到终值 |
| 有覆盖窗（置顶普通窗盖住顶部 520px） | 岛超界 **0/155** 帧，抓屏 118–128ms，主进程事件循环卡 111/132ms |
| 抓屏进行中点击展开 | 岛超界 **0/156** 帧 |
| 主进程忙等 1500ms | 岛超界 **75/156** 帧，窗口停在 171×78 长达 1.5 秒，岛已是 255×272 |
| 尺寸反复上报（±1px 抖动，每 40ms 一次） | 窗口高度到终值从 244ms 拖到 **448ms**，且之后持续在 274/275 之间来回跳（窗口高度回退 6 帧） |

用户视频1 逐帧（`.tmp/v1f/`，numpy 量岛体边界）：点击后岛高从 162 爬到 248，**每帧只 +1px，耗时约 1.7 秒**，与「220ms 补间」差 8 倍。

**两条根因**：

1. **补间会被中途重启、计时归零** [实测，`.tmp/probe-tween-restart.mjs`]：`animateTo()` 在 `tweenTimer` 已存在时只改 `tweenFrom` / `tweenStart` 就 return（`index.ts:241`），而渲染层在展开入场期间会**反复**上报尺寸（ResizeObserver 去抖 80ms + `reportCurrentSize` + 切页路径）。任何一次上报只要尺寸有 1px 差异，`set-expanded-size` 就会 `animateTo(true)` → 计时归零 → 补间从头再跑 220ms。用户机器上量到的尺寸有 ±1px 抖动，于是补间被无限续命，看起来就是「慢慢爬、像卡住」。
2. **补间被主进程阻塞时，渲染层的入场计时不会跟着停** [实测]：入场用固定 `setTimeout(260ms)` 结束（`App.tsx:3649`），结束时无条件清掉 `--entrance-w/h`。主进程一旦被卡住（`desktopCapturer.getSources` 实测 118–192ms，覆盖窗场景还会额外触发 DWM 重合成），窗口停在半途，岛却跳到全尺寸 → 被 `.island { overflow: hidden }` 裁掉，用户看到「显示不完整」。

**修法方向**：
- 补间**不因重复上报而重置计时**：目标尺寸变化时，只在「目标确实变了」且「剩余时间还有余量」时才重启，并且重启时保留已走完的进度（按当前实际窗口尺寸重新算 `tweenFrom`，`tweenStart` 不归零）。同时给上报加 1px 死区，抖动不上报。
- 入场结束条件从「固定 260ms」改成「窗口已到目标尺寸 或 超时」——窗口没长到位就继续逐帧跟随，绝不提前把岛放到全尺寸。

## 四、预期行为

1. 置物架（大图标 / 列表两种视图）里按住任意条目往外拖 → 光标带着文件图标离开岛 → 松手到剪映时间线 / 资源管理器 / 任意接受文件的应用，对端收到**这个真实文件**。
2. 架内把 A 拖到 B 上仍然是**互换位置**（原有行为不变）。
3. 两个不同的 `.lnk`（或 `.exe`）放在置物架上，各显示自己的图标；桌面图标与置物架图标一致。
4. 失效条目（文件已不在）仍显示按扩展名的占位图标，不报错。
5. 展开/收起在以下条件下都平滑：① 岛下面盖着普通应用窗口；② 底图抓屏正在进行；③ 机器较慢、主进程偶尔卡 100–200ms。
6. 展开全过程任何一帧，岛的宽高都不超过窗口（不出现被裁的扁条或缺一块）。

- 不改底图抓屏的架构（`desktopCapturer` 仍是唯一可行路径，见 `本机约束与踩坑.md` 第 61 条）。
