# SPEC：合并「卸载残留」与「软件残留」，备份与撤销统一

- 创建：2026-11-20
- 分支：`space-merge-junk`
- 前置：`SPEC-space-residue`（卸载残留）、`SPEC-space-software-residue`（只读检测）、`SPEC-space-residue-cleanup`（软件残留清理）

## 1. 目标

空间页只留一个「残留」小节，里面两段列表：卸载残留、软件残留。清理产生的东西统一进同一块「清理备份与撤销」：两类备份都按批次列出，都能逐批撤销、都能二次确认后删除。解决两个问题：

1. 软件残留目前只能撤销「最近一次」，备份在界面上看不到也删不掉；
2. 两节各有一套备份区，用户看到两个入口，分不清哪些能恢复。

## 2. 修改范围

- `src/main/softwareResidueCleanup.ts`：备份清单（多批）、按批次撤销、删除备份；`manifest.json` 增加 `restored`；撤销成功但目录保留。
- `src/main/softwareResidueStore.ts`：IPC 改为 `software-residue:undo`（带批次 id），新增 `software-residue:backups`、`software-residue:discard`。
- `src/shared/types.ts`：`ResidueCleanupBackup`、`ResidueDiscardBackupResult`；`ResidueUndoResult` 增加批次号与备份列表。
- `src/preload/index.ts`：对应三个方法。
- `src/renderer/src/settings/SpaceSection.tsx` + `settings.css`：合并小节、共享备份块、撤销后刷新列表。
- 文档：本 SPEC 自检记录、`功能清单.md` 第 16 节、`状态.md`。

## 3. 预期行为

### 3.1 合并后的结构

「系统」卡里依次是：系统垃圾 → 残留（**一张清单** + 清理备份与撤销）。不再有独立的「软件残留」卡片，也不再分「卸载残留 / 软件残留」两个小节标题。

- 一张清单同时放两类残留：卸载项、死快捷方式、空的开始菜单文件夹（一律「确定」级、都可勾选），以及服务、驱动、计划任务、目录、进程（按证据分三级，只有确定级可勾选）。
- 一个「开始检测 / 重新扫描」按钮同时跑两套扫描，一个清理按钮处理两边的勾选：只选卸载残留时直接清；选了软件残留则先提示、按钮变「确认清理」，再点才执行（UAC 只对软件残留生效）。

### 3.2 备份清单

- 只读 `%APPDATA%\lingdong-island\residue-backup\residue-*\manifest.json`；目录名必须匹配 `residue-<时间戳>-<随机>`，防止被伪造路径带偏。
- 每批显示：时间、类型（卸载残留 / 软件残留）、项数、是否已撤销。
- 读不到清单的批次不显示，也不删除。

### 3.3 撤销

- 按批次 id 撤销，不再固定「最近一次」。
- **全部恢复成功后删除该批备份目录**（2026-11-20 用户要求：复原之后备份不要留）。部分成功（例如原位置已有同名文件）时保留该批，处理掉冲突后还能再点一次撤销。
- 取消 UAC 时什么都不改，`restored` 不写。
- 撤销后只重扫受影响的那一类：卸载残留立即重扫不打断其它行；软件残留重扫一次（约十几秒，属预期）。

### 3.4 删除备份

- 删除批次目录，不可恢复；沿用卸载残留的二次点击确认（第一下变「确认删除」）。
- 只删本项目备份根目录下的 `residue-*` 目录，路径不对直接拒绝。

### 3.5 安全边界不变

- 渲染层只传批次 id；主进程校验格式并在清单里存在才处理。
- 软件残留清理的校验、备份、提权脚本规则完全沿用 `SPEC-space-residue-cleanup`。

## 4. 必要依赖

无新增依赖。

## 5. 验收条件

1. `npm run typecheck`、`npm run build` 通过。
2. 隔离实例中清理软件残留两次，备份块出现两批；撤销较早一批成功，恢复项对应正确。
3. 取消 UAC 时备份的 `restored` 不变。
4. 删除备份后目录消失，列表少一批。
5. 卸载残留原有行为不变：清理、撤销、删除备份都正常，且与新备份块共享同一区域。
6. 伪造批次 id（不存在的、带路径分隔符的）被拒绝。

## 6. 不做什么

1. 不合并两套扫描逻辑，不统一数据模型。
2. 不改卸载残留的备份位置与恢复方式。
3. 不做自动清理定时任务，不加「全部撤销」。

## 8. 追加修订（2026-11-20，按用户验收意见）

用户看到「残留 / 卸载残留 / 软件残留」三级标题后要求合成一个，于是把两个列表并成**一张清单**：

- `ResiduePanel` 合并两类数据（`MergedResidueRow`）：卸载项/快捷方式/开始菜单一律「确定」级且可勾选；软件残留按原等级，只有确定级的服务/计划任务/空目录可勾选。
- 一个「开始检测 / 重新扫描」并行跑两套扫描；一个清理按钮按勾选来源决定要不要二次确认 + UAC。
- 卸载项的类型标签改为「卸载项 / 快捷方式 / 开始菜单」，避免和软件残留的「目录」混淆。

**同一轮修掉的 bug**：行上的等级类名写作 `swr-${level}`，「需确认」行因此得到 `swr-check` 类，和勾选框按钮的 `swr-check` 撞名，导致 38 行被套上勾选框样式（`cursor: pointer`、去内边距）。改成 `swr-lv-${level}`，CSS 同步改 `.swr-row.swr-lv-definite`。[实测：改前 `selectable=11 / checks=49`，改后 `checks=11`]

**验证 [实测]**（CDP 9341/9342/9343）：标题只剩「灵动岛 / 系统 / 系统垃圾 / 残留 / 清理备份」；一张清单 49 行、11 行带勾选框；勾一行后按钮变「清理选中项（需要管理员）」，第一次点击只出确认提示、按钮变「确认清理」，未弹 UAC；图例与备份块照常。

## 9. 追加修订二（2026-11-20，用户验收反馈）

1. **撤销后不留备份**：`undoResidueCleanup`（软件残留）与 `undoResidueBackup`（卸载残留）在全部恢复成功后直接删除该批备份目录；部分恢复（原位置同名文件、注册表导入失败等）才保留，方便修掉冲突后重试。`restored` 标记只对旧备份仍生效。
2. **「只报告」标签**：没有勾选框的行在名字后加一个「只报告」灰标签，悬停给出原因——驱动「删错可能让硬件不能用」、进程「不结束运行中的进程」、非空目录「目录里有内容，不自动删」、其余「证据不足」。复制清单时同样带上这句原因。

**验证 [实测]**（CDP 9344，自造一批卸载残留备份，不动真实数据）：`residueUndo` 返回 `ok:true`、`warnings:[]`，文件搬回原位，批次目录已删除，`residueBackups()` 变空。同一实例扫描后：49 行里 11 行可勾选、38 行带「只报告」标签且 `title` 为对应原因（如「驱动删错可能让硬件不能用，只报告」）。

**未验证**：软件残留的撤销（要 UAC）；打包版。
