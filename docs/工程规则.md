# 工程规则

本文件是工程规则的**唯一正文**。根目录 `README.md`、`AGENTS.md`、`docs/Spec/` 下的规格文件都引用本文件，不再各自复述一套。

适用范围：本仓库的全部开发工作。产品事实另见 `docs/facts/`，两者互不重叠——本文件讲「怎么做工程」，`docs/facts/` 讲「产品是什么」。

---

## 一、分支与基线

1. `main` 保持稳定可运行。任何一步开发都不直接往 `main` 上提交。
2. 每项开发从**确认的基线**创建独立任务分支：`git switch -c <任务名> main`。任务名与对应 SPEC 同名，便于对照。
3. 开发与自检都在任务分支上进行。分支上允许中间状态提交（WIP），但交付验收的必须是分支上某一个**固定提交**。

## 二、SPEC 先行

1. 每次开发（一个新版本，或一个明确的开发任务）在**动手写代码之前**，先在 `docs/Spec/` 建立对应的 SPEC。
2. SPEC 必须写清六项：目标 / 修改范围 / 预期行为 / 必要依赖 / 验收条件 / 不做什么。
3. SPEC 通过引用 `docs/facts/` 里的产品事实来说明背景，**不复制**整套产品设定。事实变了就更新事实文档，SPEC 只改本次的差异部分。
4. 没有 SPEC 就不开工。临时改动、试错探针可以不打 SPEC，但不得留在交付提交里。

## 三、自检与独立验收分离

1. **研发自检**：实现方在交付前自己跑一遍——类型检查、构建、适用的自动化测试（本项目为 `scripts/e2e-*.mjs`）。自检结果记录在 SPEC 的「自检记录」一节，必须写清「跑了什么命令 / 结果 / 哪些没验证」。**只跑受本次改动影响的测试，不必每轮全量**（全量留到第八节的批量验收前跑一次）。
2. **独立验收**：由**未参与本次实现**的会话或人，针对**同一个固定提交**逐条核对 SPEC 的验收条件，结果记录在 SPEC 的「验收记录」一节。
3. 自检和验收**分别记录**，不得合并成一句「已通过」，也不得用自检结果代替验收结论。
4. 验收发现问题 → 回到任务分支修复（已合并的就在 `main` 上开修复分支）→ 重跑受影响的检查（不必全量，但必须覆盖改动路径）→ 在同一个 SPEC 下补记新一轮结果。
5. **验收时机按批进行（2026-11-11 用户决定）**：不再每做完一项功能就做一轮独立验收。日常开发只做「自检 → 预览版给用户试 → 用户确认 → 合并回 `main`」；攒完一批功能后，对整批做**一次**独立验收，针对合并后的 `main` 提交，一次覆盖这一批的全部 SPEC。理由：用户试用能发现主流程问题，但发现不了多路径/多状态缺陷（2026-11-11 音乐页的多会话读不到、设置窗口自启不同步都属于这类），所以独立验收不能取消，只能攒。**代价**：中间合并的功能在上 `main` 时没被独立审过；批量验收若查出是前面某功能的问题，就在 `main` 上开修复分支修，不推翻重来。

## 四、角色职责

| 角色 | 负责什么 | 不负责什么 |
|---|---|---|
| 开发 | 按 SPEC 实现、写自检记录、交付固定提交 | 判定自己是否通过验收 |
| 自检 | 实现方本人执行命令、核对产物、记录证据与未验证范围 | 代替独立验收 |
| 独立验收 | 换一个会话/人，对固定提交逐条核对 SPEC 验收条件 | 顺手改代码、扩大范围 |
| 合并 | 验收通过后，按用户授权把分支合回 `main` | 决定是否上线 |

具体由哪些人或 AI 会话扮演，由用户指定；未指定时默认：实现方自检，另起会话验收，合并在授权后由当前会话执行。

## 五、合并与上线

1. 合并回 `main` 需要用户明确授权，前置条件是验收记录已写明通过。
2. **合并 ≠ 上线。** 发版、安装到用户机器、对外发布都要用户单独明确确认；本项目的「上线」具体指执行 `npm run dist` 打包并安装到 `D:\软件\灵动岛\`。
3. 只记录**实际做过**的操作和**实际看到**的结果。没跑的命令不写「已通过」，没看的界面不写「已验证」，一律归入「尚未验证的范围」。

## 六、文档与复用

1. 修改涉及产品事实、接口约定或数据规则时，同步更新 `docs/facts/` 里对应的责任文档（同一事实只在一处维护，其他位置用链接引用）。
2. 动手前先检查已有代码、组件、脚本能否复用；能复用就复用，不重新造。
3. 不顺便修改无关功能。发现顺手可改的其它问题，记下来另开 SPEC，不混进本次提交。

## 七、证据与清理

1. 保留必要的交付证据：自检命令输出摘要、截图/探针结果、失败日志。失败证据同样要留——它能说明排查过什么。
2. 收尾时清理本次不再需要的临时文件、测试服务、残留进程。本项目约定：一次性脚本与截图放 `.tmp/`（已被 Git 忽略），残留的 electron 进程与 CDP 端口用完即关。
3. 任务验证并合并后，再删除对应的任务分支与工作树（本仓库为单工作树，主要是删分支）：`git branch -d <任务名>`。

## 八、交付给用户时必须给的三样（用户要求，2026-11-04）

每一轮交付给用户时：

1. **做了什么**：逐条列本轮改动（界面哪一页、什么行为）。
2. **怎么验证**：给用户可亲手操作的步骤（点哪里 → 会看到什么），并注明哪些点**只有真人能验证**（如真实拖拽、通知到达）。
3. **用户在哪看**：默认给**开发预览版**（`npm start`，约 2 秒起来），交付前先停掉安装版实例（两者共用同一份数据，同时开会出两个岛）。**「给预览版」包含两件事，缺一不可（2026-11-16 用户 m03335 指出助手多次只说不做）**：①**真的把预览版进程起来并确认它活着**——`Get-Process electron` 有主窗口标题「灵动岛」的进程、窗口可见；②**在交付话术里告诉用户它已经开着了、可以直接去看**。只写「你可以用 `npm start` 试」而没起进程，视为未交付。起预览版的固定姿势见第九节。**打包装机改为按批进行**（2026-11-11 用户决定）：攒到一批功能做完、批量验收通过后打**一次**安装包；用户明确要一个能长期用的版本时也立刻打。理由：打包 + 静默安装 + 启动复验约 10 分钟，而预览版 2 秒就能让用户看到，试出问题还能立刻改。**预览版的两个固有差异必须在交付时说明**：①在预览版里打开「开机自启」写入的是**项目目录路径**，重启会拉起预览版而非安装版，测自启要等装机后再测；②预览版没有安装器的身份，任务栏/系统通知的图标与名称可能与装机版不同。

涉及数据或行为变化时，额外说明影响（如卸载不删数据、旧数据是否迁移）。

## 九、本项目的固定操作约定

- 打包必须走国内镜像，否则证书/超时失败：
  ```powershell
  $env:ELECTRON_MIRROR='https://npmmirror.com/mirrors/electron/'
  $env:ELECTRON_BUILDER_BINARIES_MIRROR='https://npmmirror.com/mirrors/electron-builder-binaries/'
  npm run dist
  ```
- 自动化启动 electron 前必须先清掉继承来的环境变量，否则退化成纯 Node 秒退：
  ```powershell
  Remove-Item Env:ELECTRON_RUN_AS_NODE -ErrorAction SilentlyContinue
  ```
- **交付前起预览版给用户看的固定姿势**（2026-11-16 用户 m03335 定，见第八节第 3 条）：
  ```powershell
  Get-Process 灵动岛,electron -ErrorAction SilentlyContinue | Stop-Process -Force   # 先停安装版，避免两个岛
  Remove-Item Env:ELECTRON_RUN_AS_NODE -ErrorAction SilentlyContinue
  Start-Process -FilePath "cmd.exe" -ArgumentList '/c','npm start > .tmp\preview.log 2>&1' -WorkingDirectory $PWD -WindowStyle Hidden
  Start-Sleep -Seconds 12
  Get-Process electron | Select-Object Id,MainWindowTitle     # 必须看到 MainWindowTitle = 灵动岛
  ```
  三条注意：①**不能让 agent 会话直接跑 `npm start`**——它是长驻进程，会占住会话；要用 `Start-Process` 脱离会话（`cmd.exe /c npm start` 是为了拿 `start` 脚本里的 `electron-vite preview`）；②**`npm start` 不接受 `--remote-debugging-port` 等 electron 参数**（`electron-vite preview` 会报 `CACError: Unknown option --remoteDebuggingPort`），要 CDP 探针就改用 `node_modules\electron\dist\electron.exe . --remote-debugging-port=9321`；③`npm start` 会**先构建再起**，`src` 改动不用自己先跑 `npm run build`，但等的时间比 2 秒长（约 10–15 秒），起来后看 `.tmp\preview.log` 确认没有报错。
- e2e 与 CDP 探针统一用端口 `9321`（9222/9223/9230 已被占用）。
- **打包与验收都按批进行**（2026-11-11 用户决定，见第三节第 5 条与第八节第 3 条）：日常开发用预览版 `npm start` 给用户看，不打包；攒完一批功能后先做一次独立验收，再打一次安装包。**唯一例外**：用户明确要求「现在就要能长期用的版本」时，立刻打包安装。
